# 账号恢复与本机维护

更新：2026-11-13。实现复用锁定的 Better Auth 1.7.18 官方 `sendResetPassword`、`requestPasswordReset`、`resetPassword` 及数据库钩子；不修改依赖源码、不直接写密码哈希、不伪造管理员会话。

## 用户忘记密码

登录页的“忘记密码”接受登记邮箱。正常配置真实邮件服务后，邮件指向配置的 `BETTER_AUTH_URL` 下 `/admin?auth=reset&token=...`。来源固定在服务端，客户端不能指定跳转域名或路径。

恢复链接有效期为15分钟，只能成功使用一次；新密码要求12至128个字符。成功后该账号全部旧会话失效，用户需用新密码重新登录，不会自动登录。发送及修改前都会复核当前账号；已停用、角色不受支持、邮箱/角色/密码自申请后发生变化的旧链接不能使用。成员角色变更后应重新申请。

登录页最先将链接令牌取到组件内存并移除地址栏参数；不会放入 localStorage、sessionStorage 或一般设置。页面和恢复接口使用 `Referrer-Policy: no-referrer`，接口响应均 `Cache-Control: no-store`。部署代理、访问日志及监控也应屏蔽恢复链接的 query，避免在进入应用前就记录令牌。

无论邮箱未知、停用、未配置 SMTP 或投递失败，申请接口都给出同样的“如果该邮箱可用于恢复，系统会尝试发送恢复邮件”回执，不能据此判断账号存在，也不声称邮件已经送达。模拟邮件模式仅做本机验证，不会真实外发；审计将模拟和真实投递分别标记，不写邮箱、令牌或邮件正文。

## 邮件配置与投递边界

恢复邮件复用“站点设置 → 邮件通知”的服务器、端口、认证与安全配置。即使询盘自动通知关闭，只要 SMTP 配置完整，仍可发送恢复邮件。收件人只能是该账号当前登记邮箱，与询盘通知收件人无关。未配置、失效配置、连接失败或账号状态变化时，已生成的恢复令牌会作废。

公开申请接口先验证请求、限频并返回统一回执，再通过 Next `after` 跟踪账号查询与邮件投递。SMTP 慢或账号未知不会形成响应耗时差异。本实现不是持久邮件队列：进程在回执后异常退出可能丢失投递，用户可稍后重试；不承诺重启后自动补发或邮件最终送达。

所有请求必须为配置来源的同源 JSON POST；正文按流限制为32 KiB，不接受额外字段。申请按所有请求每分钟30次、邮箱摘要每15分钟3次限制；重置按所有请求每分钟60次限制，计数持久保存在现有 `cms_public_rate`。邮箱键为使用站点认证密钥的 HMAC，不记录原邮箱。共享总限额可能在异常流量期间暂时影响所有用户，部署时仍需代理侧防滥用；此处不以可伪造代理头作为可靠身份。

## 唯一管理员丢失密码或 SMTP 不可用

可用的另一名管理员可在成员管理重置其他成员密码。没有其他可用管理员时，拥有服务器终端权限的维护人员可使用受控本机恢复。重复运行 setup 不会重置已有账号。

本机恢复只接受已经存在且未停用的 `admin`，不会创建账号、提权或解禁。必须停止网站实际 Node 服务，核对该实例数据目录、固定认证密钥和**应用实际监听端口**。端口探测只能辅助检查当前本机端口；填写错误端口、容器/远程实例或其他进程行为不能由该探测证明安全，操作者必须完成真正的维护窗口。

在出海建站 AI 源码根目录运行。以下路径和邮箱请替换为实际维护配置。

```powershell
npx tsx scripts/auth-recover.ts --env-file "C:\path\to\instance.env" --email "admin@example.invalid" --port 3200 --backup-dir "C:\path\to\new-recovery-backup" --acknowledge-stopped
```

命令要求再次输入邮箱和两遍不回显的新密码。密码不能作为命令行参数或环境变量传入。无人值守场景仅允许 `--stdin` 从受控管道读取 JSON，字段为 `email`、`confirmationEmail`、`newPassword`、`confirmPassword`；不要把带真实密码的 JSON 写入终端历史、脚本、日志或工单。标准输入最多8192字节。

配置读取指定的 `--env-file`，默认使用已有 `.env.local`，进程已有环境优先；如文件与进程的认证密钥不同则拒绝。恢复不会生成或轮换密钥。数据目录和数据库必须已经存在且不能经过符号链接/目录连接；先只读检查既有管理员，再确认本机 IPv4/IPv6 端口无监听，取得仅用于防止两个恢复命令并发的 `.auth-recovery.lock`，最后才做完整备份。该锁不是部署文件锁，不能代替停服。

备份必须位于数据目录外且目标不存在；包含 SQLite 和媒体，不包含环境文件与认证密钥，匹配密钥需另行安全保管。备份完成后才打开业务数据库并调用原生恢复申请及重置：令牌仅在当前 CLI 进程内存中捕获，立即一次性消费；不经真实邮件、不输出令牌、不建立登录会话。流程撤销全部旧会话并保留业务、发布和配置数据。公开匿名申请的限频不会阻断已确认维护窗口的本机恢复。

成功输出只含恢复状态、备份目录和重新登录提示。确认后启动网站，使用新密码登录并核查成员、内容和发布记录。失败不会打印第三方原始错误或凭据；先按提示核对，不要删库重新初始化。异常退出如留下 `.auth-recovery.lock`，确认所有恢复进程已退出且网站仍停服后，由维护人员清理；不能在运行中强行删锁。

## 接口与私有存储

| 接口 | 请求与结果 |
| --- | --- |
| `POST /api/account-recovery/request` | `{ email }`，正常回执 `{ accepted: true, message }`；邮箱格式/字段错误422、来源403、过量429 |
| `POST /api/account-recovery/reset` | `{ token, newPassword }`，成功 `{ reset: true, message }`；无效/过期/重放链接400、密码/字段错误422、来源403、过量429 |

原生恢复 HTTP 端点仍不在 `/api/auth/*` 白名单内，管理插件端点仍不公开。恢复不要求添加认证表：原生 `auth_verification` 保留 `reset-password:<token>` 的 userId 值；额外状态戳另用 `studio-recovery:<sha256(token)>` 标识，保存 userId、邮箱、角色和当前凭据摘要。重置前钩子与实际写入钩子均复核；原生适配器消费令牌和写密码，成功后清理独立元数据。该数据库和备份仍是敏感私有数据，不属于网站快照或分发包。

## 验证与升级

```powershell
npx tsx --test tests/account-recovery.test.ts
npm run typecheck
```

隔离单测使用随机临时数据库、合成账号和 JSON 邮件传输，验证原生 SDK 一次性/过期/并发消费、角色/邮箱/停用/密码变化失效、全会话撤销、泛化回执、限频、关闭询盘通知时仍可恢复、维护守卫，以及真实子进程 stdin CLI 的备份与数据保持。测试不真实发信，也不访问正式数据库。HTTP 和浏览器恢复流程由全站集成测试统一运行，不提供生产令牌读取接口。

升级 Better Auth 必须保留官方配置及独立模块，并在副本验证 `requestPasswordReset/resetPassword` 的参数、原生 verification 标识和值、单次消费顺序、账号写入钩子上下文及会话撤销；升级 Next 必须验证 `after` 的响应后工作仍被跟踪。重点回归原生 HTTP 端点仍关闭、所有异常不泄漏令牌/账号、重置不自动登录、CLI 不需要管理员会话。官方若提供等效的状态绑定能力，应评估迁回官方实现。回滚使用配套旧代码、环境密钥及恢复前完整备份；页面发布回滚不会恢复账号密码或会话。
